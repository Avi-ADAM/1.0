## 1. הבעיה

אלפי מפתחים כותבים קוד פתוח בחינם. חברה מאמצת אותו, בונה עליו מוצר ומרוויחה —
והמפתחים לא רואים מזה כלום. הכלים שקיימים היום מטפלים רק בחלק מזה:

| כלי קיים | מה הוא נותן | מה חסר |
|---|---|---|
| GitHub / GitLab | קוד, PR, Issues, CI | אין שם מושג של בעלות או ערך |
| GitHub Sponsors / Open Collective | תרומות | תרומה היא נדבה — לא חלק בשווי, ולא קשורה למי שעשה את העבודה |
| Bounties (Algora, IssueHunt) | תשלום לכל Issue | חד־פעמי, בלי חלק בהצלחה העתידית |
| רישיונות BSL / Fair Source | מגבילים שימוש מסחרי | ההכנסה הולכת לחברה שמחזיקה בקוד, לא לתורמים |

**מה ש-1lev1 מוסיפה:** היא רושמת **מי תרם מה**, דואגת **להסכמה** על השווי של כל
תרומה, ו**מחלקת את ההכנסה** לפי זה. כל המנגנונים האלה כבר קיימים ברקמה (משימות,
שעות מאושרות, `Decision`, restime, מכירות, חלוקות). התכנית הזאת לא בונה מערכת
חדשה — היא מחברת את מה שכבר קיים אל עולם הקוד.

### עיקרון מנחה

> **את GitHub לא בונים מחדש.** הקוד נשאר ב-GitHub. 1lev1 היא הרישום של העבודה,
> של ההסכמות ושל השווי.
> GitHub יודע *מה* נבנה, ו-1lev1 יודעת *של מי* זה.

## 2. רישיון רקמה (החלק העקרוני)

### 2.1 הרעיון

רישיון MIT מתיר לכל אחד לעשות בקוד מה שהוא רוצה. הרעיון כאן הפוך בדיוק בנקודה
הזאת:

- **מותר:** לקרוא את הקוד, לעשות fork כדי לתרום, להריץ לשימוש אישי, ללמידה
  ולבדיקה, ולהוסיף קוד — כל תרומה נרשמת כחלק בשווי הרקמה.
- **צריך הסכמה של הרקמה:** שימוש מסחרי ושימוש בסביבת production. ההסכמה היא
  **רישיון שקונים מהרקמה**. בפועל זו `Sale` רגילה, והכסף שלה נכנס לחלוקה לפי
  האחוזים של כל אחד — כולל התורמים.
- **גם תמיכה בלי קוד אפשרית:** מי שלא כותב קוד יכול לתמוך בעשייה דרך דף התמיכה
  הקיים (`/project/[id]/support`).

זה לא "קוד פתוח" לפי ההגדרה של OSI, ו**אסור לקרוא לו כך**. קהילת המפתחים רגישה
מאוד לשימוש לא נכון במונח. המינוח הנכון הוא **source-available / fair-source**,
והמסר השיווקי: *"הקוד גלוי, ומי שתורם לו הוא שותף"*.

### 2.2 הרקמה בוחרת רישיון, והבחירה מתקבלת בהסכמה

לא כל רקמת קוד רוצה להגביל שימוש. הרישיון יהיה פרמטר של הרקמה, שנקבע ומשתנה רק
דרך `Decision` (הצבעה של כל הרקמה) — אותו מנגנון כמו שאר פרמטרי הרקמה:

| `Project.codeLicense` | משמעות | מאיפה מגיע הכסף |
|---|---|---|
| `null` / `none` | לא הוגדר (legacy) | — |
| `mit` / `apache` | קוד פתוח אמיתי | תמיכה, חסויות, שירותים, bounties |
| `rikma` | רישיון רקמה (§2.1) | רישיונות מסחריים + כל מה שבשורה הקודמת |
| `rikmaDelayed` | רישיון רקמה שהופך ל-MIT/Apache אחרי N שנים (כמו BSL) | כמו `rikma`, בחלון זמן מוגבל |

כל גרסה של הקוד נשארת תחת הרישיון שהיה בתוקף כשהיא פורסמה. אם הרקמה מחליפה
רישיון, השינוי חל רק מכאן והלאה.

### 2.3 הסכם תורם (Contributor Rikma Agreement)

כדי שהרקמה תוכל למכור רישיון, צריך שהזכויות על הקוד יהיו אצלה. כל תורם מאשר פעם
אחת, בזמן קישור חשבון ה-GitHub (§3.2):

1. הוא נותן לרקמה רישיון להפיץ את התרומה שלו תחת הרישיון שהרקמה בחרה.
2. בתמורה, התרומה נרשמת כעבודה ברקמה ומזכה בחלק בשווי — אחרי הסכמה (§4).
3. הזכויות המוסריות וה-attribution נשארים שלו.

### 2.4 ⚠️ לפני שמפרסמים — ייעוץ משפטי

- נוסח הרישיון והסכם התורם **חייבים** לעבור עורך דין (ישראל + ארה"ב לפחות). לא
  מפרסמים תבנית רישיון לפני שזה קרה.
- לבדוק אם "חלק בשווי רקמה" נחשב נייר ערך בתחומי שיפוט מסוימים, ומה ההשלכות
  המיסויות לתורם מחו"ל.
- רישיון לא אוכף את עצמו. הערך בפועל מגיע מחברות שרוצות לעמוד בדרישות החוק, לא
  מתביעות. לכן מסלול הרכישה (§5.1) צריך להיות קל יותר מהפרה.

## 3. חיבור הקוד

### 3.1 מאגר מחובר (GitHub App)

- הלינק שכבר קיים (`Project.githublink`) הוא נקודת ההתחלה, והוא כבר מוצג (S0).
- השלב הבא הוא **GitHub App** ולא טוקן OAuth של משתמש. ה-App מותקן על ה-repo או
  על ה-org, ומקבל רק את ההרשאות שבחרו לתת לו: issues, pull requests, metadata,
  וכתיבת comments.
- Webhook ב-`/api/v1/github/webhook`:
  - מאמת `X-Hub-Signature-256` מול סוד שנקרא דרך `$env/dynamic/private`, לא דרך
    `process.env` (ר' הזיכרון על vite dev).
  - ממפה `installation.id` → `project`.
  - מבצע פעולות **רק** דרך `actionService.executeAction` עם principal מסוג
    `apiKey`/`serviceAdmin`, ועם `access` מפורש בכל config.
- Collection חדש, `project-repo`: `project`, `provider` (`github` בהתחלה),
  `owner`, `name`, `installationId`, `defaultBranch`, `license`.
  לרקמה יכולים להיות כמה repos.

### 3.2 זהות: חשבון GitHub ↔ משתמש 1lev1

- חיבור OAuth בהגדרות (`/me/settings`) שומר `githubId` (מספרי, קבוע) ו-`githubLogin`.
  השדה `githublink` הקיים הוא URL חופשי, ואי אפשר לסמוך עליו לזיהוי.
- **תרומות שעוד לא נתבעו:** PR של מי שעוד לא קישר חשבון נרשם תחת ה-login שלו
  ב-GitHub. כשהוא מקשר, התרומות "מחכות לו" והוא יכול לתבוע אותן. זה גם ערוץ
  גיוס (§6): *"יש לך תרומות שמחכות לך ב-1lev1"*.

### 3.3 מה נבנה ב-S2 ואיך מפעילים

**הזרימות**
- **קישור חשבון:** `/me/settings` → `/api/v1/github/connect?intent=link` → OAuth ב-GitHub →
  `/api/v1/github/callback`. נשמרים רק `githubId`, `githubLogin`, `githubLinkedAt`. הטוקן של המשתמש לא נשמר.
- **חיבור מאגרים לרקמה:** `/moach/[pid]/code` → `connect?intent=install&projectId=` (בודק חברות) →
  התקנת ה-App → callback. ה-callback מאמת שהמשתמש המחובר הוא מי שהתחיל, שה-`installation_id`
  באמת נגיש לו (`/user/installations`), ושהוא עדיין חבר ברקמה. רק אחרי זה נכתבות השורות.
- **Webhook:** חתימה נבדקת על ה-body הגולמי. מטופלים רק `installation` (השהיה, ביטול השהיה, מחיקה) ו-
  `installation_repositories`. כל השאר מקבל 202 ונשאר ל-S3/S4.
- **כלל:** מאגר שייך לרקמה אחת לכל היותר. מאגר שעדיין מחובר לרקמה אחרת לא מועבר.
- **כתיבה:** כל כתיבה של זהות או מאגרים עוברת דרך actions שזמינים רק ל-`serviceAdmin`, כך שלקוח
  לא יכול לטעון לחשבון GitHub של מישהו אחר. ניתוק מאגר וביטול קישור הם פעולות של חבר.

**הגדרה (פעם אחת):** מדריך מלא, שדה אחרי שדה, ב-[`GITHUB_APP_SETUP.md`](GITHUB_APP_SETUP.md).
- **host:** כל נתיבי GitHub רצים על **`api.1lev1.com`**, וה-secrets יושבים רק שם. הדפים ב-www
  (Vercel) שולחים את המשתמש ל-api ומקבלים אותו בחזרה.
- **env:** רק ב-`/home/ubuntu/api/.env`. ב-Vercel לא מוסיפים כלום.
- **Strapi:** ל-API token הרשאות `find`, `findOne`, `create`, `update` על `project-repo`.

## 4. העבודה עצמה: Issues, PRs, Reviews

### 4.1 Issue → מטלה או משימה פתוחה

אין צורך לבנות חדש, כי `PLAN_EXTERNAL_TASKS_API` כבר פותר את זה:

| סוג Issue | הופך ל- | איך |
|---|---|---|
| issue רגיל ב-repo מחובר | `Act` בתוך משימה בתהליך מסוג "תחזוקה" | `createTask`, עם `externalId = gh:owner/repo#123` (אידמפוטנטי) |
| issue עם label `1lev1:open` | `open_mission` ציבורית עם הערכת שעות/שווי | מופיע בלוח "מה הרקמה מחפשת עכשיו" ובדף `/join` |

הסנכרון דו־כיווני:
- issue נסגר ב-GitHub → הצעה לסמן את ה-Act כבוצע (`naasa`). זו הצעה, לא סגירה
  אוטומטית.
- מטלה נסגרת ב-1lev1 → comment על ה-issue.

### 4.2 PR ממוזג → תביעת עבודה, ולא אחוזים אוטומטיים

זו הנקודה הכי רגישה בתכנית. **אסור ששורות קוד יהפכו לאחוזים באופן אוטומטי.**

1. PR ממוזג של חבר מקושר פותח **טיוטת תביעה** על המשימה הקשורה. המשימה מזוהה לפי
   ה-issue שה-PR סוגר, לפי שם ה-branch, או בבחירה ידנית.
2. שעות מטיימר שרץ על אותה משימה מצורפות לתביעה אוטומטית. זה כבר קיים (MCP / timers).
3. **הצעה** להיקף העבודה (גודל ה-PR, כמות reviews, הערכת Mission AI) מוצגת
   **כהמלצה בלבד**. היא אף פעם לא הערך הסופי.
4. התביעה עוברת את מסלול השעות המאושרות הקיים (`finiapruval`):
   **אישור · צ'אט · נגדית**, ושתיקה עד `restime` = הסכמה. בלי וטו.
5. רק שעות **מאושרות** מזיזות אחוזים. זה אותו כלל כמו ב-`Sale` וב-stipend.

**Reviews הם עבודה.** review שמאשר או מבקש שינויים פותח תביעה קטנה לסוקר, באותו
מסלול. בלי זה, מי שמתחזק את הפרויקט (ובעיקר עושה reviews) מקבל פחות ממי שכותב
PRs.

### 4.3 תורם מבחוץ

PR ממוזג של מי שעוד לא חבר ברקמה נותן לו בחירה:

- **להצטרף כשותף עם התרומה הזאת:** נפתחת הצעה עצמית
  (`source:'selfNomination'`, PLAN_SELF_NOMINATION), כשהתרומה עצמה היא "מה אני
  מביא".
- **תרומה במתנה:** נרשם כתומך (supporter) בלי חלק בשווי, עם attribution מלא.
- **לא עכשיו:** התרומה נשארת "לא נתבעה" (§3.2), והזמנה נשארת פתוחה.

"החברות הולכת אחרי ההתחייבות האחרונה" (PLAN_OBJECT_ARCHIVAL) נשאר בתוקף: PR אחד
לא משאיר מישהו חבר לנצח בלי מה שנצבר לו.

### 4.4 אינטגרציות שמייצרות מטלות

כל אלה עוברים דרך `createTask` הקיים:
- CI שנכשל על `defaultBranch` → Act למי שמחזיק בתפקיד "build/CI".
- התראת אבטחה (Dependabot / code scanning) → Act דחוף.
- Release שתויג → עדכון לרקמה, ואופציונלית הצעה לחלוקה אם הרליס קשור למכירה.

### 4.5 טאב "קוד" במוח

`/moach/[pid]/code`:
- ה-repos המחוברים וסטטוס ה-App.
- Issues ↔ מטלות/משימות, והפערים ביניהם.
- **PRs שממתינים לתביעה** — הרשימה הכי שימושית בטאב.
- תורמים: מקושרים מול לא מקושרים, ומה נתבע/אושר לכל אחד.
- הרישיון הנוכחי, ו-Decision פתוח לשינוי שלו אם יש.

הטאב נוסף ל-nav של `moach/[projectId]/+layout.svelte` בתבנית של הטאבים הקיימים.

## 6. שיווק ונתינה לקהילת המפתחים

### 6.1 המסר

> **"הקוד שלך, החלק שלך."**
> מי שבונה את הקוד הוא שותף בו — גם אחרי שחברה מתחילה להרוויח ממנו.

### 6.2 ערוצים

- **Dogfooding:** ה-repo של 1lev1 עצמה כרקמת קוד, שהתורמים שלה צוברים חלק בשווי.
  זו ההוכחה הכי חזקה שיש.
- **Badge ל-README:** `/api/badge/[pid].svg`, למשל "rikma · 14 partners ·
  contributors own 38%". כל README שמציג אותו מפרסם את 1lev1.
- **מחשבון "כמה התורמים שלך היו מחזיקים"** מההיסטוריה של repo ציבורי: קריאה בלבד,
  בלי חשבון. זה ה-hook לפוסטים ב-Show HN / dev.to / Reddit.
- **פיילוט:** 5–10 פרויקטים פתוחים קיימים שהמתחזקים שלהם שחוקים (קל למצוא —
  "maintainer burnout"). ליווי צמוד, ואחר כך case study.
- **GitHub Marketplace:** רישום ה-App, וה-Skill/MCP הקיימים (`PLAN_MCP_SKILL`)
  כנקודת כניסה של מפתח שכבר עובד עם סוכן.
- **Discovery:** מסנן "רקמות קוד" בדפי הגילוי ובמפה.
- **חינם לרקמות קוד פתוח אמיתי** (`mit`/`apache`), בלי site-share. זו הנתינה
  לקהילה, וזה גם ערוץ השיווק.

### 6.3 Genesis — פרויקט קיים עם היסטוריה

פרויקט שכבר קיים שנים ומגיע ל-1lev1 מקבל **הצעת חלוקה התחלתית** שמיובאת מההיסטוריה
(commits, PRs, reviews). מתייחסים אליה כמו ל-snapshot של T6 בלי הורה: **הצעה
בלבד**, `Decision` של כל הרקמה, ותורמים לא מקושרים מקבלים הזמנה לתבוע.

|---|---|
| **ספאם של PRs בשביל אחוזים** | שום אחוז בלי הסכמה (§4.2); ברירת מחדל של שווי נמוך; rate-limit לתביעות של לא-חברים |
| **"שווי" של קוד** — שעות מול תוצאה | התביעה היא שעות × תעריף המשימה, כמו בכל רקמה. אפשר להתווכח עליה ב-נגדית |
| **קוד שסוכן AI כתב** | העבודה של מי שהפעיל את הסוכן — שעות טיימר + review. לא שורות |
| **אכיפת הרישיון** | §2.4 — להפוך רכישה לקלה יותר מהפרה, לא לבנות על תביעות |
| **תגובת הקהילה למונח "open source"** | לא משתמשים בו לרישיון `rikma` (§2.1) |
| **ToS ו-rate limits של GitHub** | App עם הרשאות מינימליות, webhook במקום polling |
| **פרטיות** | לא שומרים אימיילים מ-commits; רק `githubId`/`login` ציבוריים |
| **Strapi** | enum-ים חדשים → `null = legacy` בכל filter; collection חדש = שתי הרשאות (Authenticated + API token); `validate:qids` לא בודק queries |
