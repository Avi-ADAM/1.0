## 1. מה כבר קיים — מיפוי מדויק

זה לא רקע. כל שורה כאן היא רכיב שהתכנית **משתמשת בו כמו שהוא**, ולכן
מגדירה את היקף העבודה האמיתי.

### 1.1 המוח — החישוב כבר כתוב

`src/routes/(reg)/hub/+page.server.ts` מחשב, בצד השרת, בדיוק את הרשימה
שהמשתמש ביקש:

```ts
export interface HubKpi {
  votes: number;          // הצבעות שלא הגבת להן   ← "והכי חשוב כך וכך הצבעות"
  urgent: number;         // מתוכן, כאלה שנותרו להן פחות מ-24 שעות
  suggestions: number;    // משימות פעילות שלי
  activePurchases: number;
  activeSales: number;
}
```

- `needsOrderedVote` (שורה 67) — לפריטים עם סבבי משא ומתן (`pendms`,
  `tosplits`, `sheirutpends`): המשתמש עדיין חייב הצבעה אם אין לו הצבעה
  ב-`order` הנוכחי.
- `needsSimpleVote` (שורה 79) — לפריטים בלי סבבים (`finiapruvals`,
  `askms`, `maaps`, `decisions`): אין לו רשומת הצבעה בכלל.
- `isUrgent` (שורה 57) — `timegrama.date` בתוך 24 שעות.
- `topFive` — ממוין דחוף-תחילה, ואז לפי הדדליין הקרוב, ואז לפי הוותק.
- כל פריט נושא `type` שהוא ערך ה-`ani` של כרטיס הלב, כדי לייצר deep-link:
  `/lev?focus=<type>&project=<projectId>`.

השאילתה היחידה שהוא מריץ היא qid `85levHubSummary`
(`src/routes/api/send/qids.js:10503`), שכבר מסומנת
`allow: ['user', 'serviceAdmin']` ב-`qidsAccess.js` — כלומר **השירות יכול
להריץ אותה בשם המשתמש כבר היום, בלי שינוי הרשאות**.

> **המשמעות:** `processHubSummary` צריך לצאת מקובץ ה-`+page.server.ts`
> ולעבור ל-`src/lib/server/digest/` (או ל-`src/lib/hub/`), כדי ששני
> הצרכנים — עמוד ה-hub והבריף — יקראו אותו קוד. פיצול לשני חישובים הוא
> בדיוק הבאג שתואר ב-TIMEGRAMA §1 ("הלוגיקה משוכפלת… שתי הדרכים יכולות
> להתפצל, ולמעשה כבר התפצלו").

### 1.2 הטקסונומיה — איזה זני פריטים קיימים

`src/lib/utils/levSliceRegistry.ts` מגדיר את כל הזנים ואת קבוצת המיקוד
הווירטואלית:

```ts
export const LEV_FOCUS_GROUPS = {
  votes: ['pends', 'fiapp', 'askedResources', 'wegets', 'decisions', 'halukas', 'sheirutpends']
};
```

זו **ההגדרה הרשמית** של "הצבעה ממתינה" באתר, והבריף חייב להשתמש בה ולא
להמציא רשימה משלו.

### 1.4 מדיניות שליחה — יש כבר תקדים מלא

`src/lib/server/matching/emailPolicy.ts` הוא **בדיוק המודל** שהבריף צריך:

```ts
export const MAX_SUGGESTION_EMAILS_PER_USER_PER_DAY = 3;
export const SEND_WINDOW = { startHour: 8, endHour: 21 };
export const SITE_TIMEZONE = 'Asia/Jerusalem';
```

ואת ה-dedup הוא עושה בלי קולקציית ניהול נפרדת — הוא סופר `notifiedAt`
על שורות ה-`match-suggestion` הקיימות (qid `213recentSuggestionEmailCounts`).
פונקציה טהורה, יש לה טסטים, והיא מודל לחיקוי.

`src/lib/server/matching/notify.ts` הוא התקדים לשליחה מרוכזת שאינה עוברת
דרך `ActionConfig.notification` — בדיוק המקרה של הבריף.

### 1.6 הפריסה בפועל

`docker-compose.api.yml` — על ה-VPS (`ubuntu@18.159.130.31`) רצים:
`sveltekit-api` (adapter-node, `127.0.0.1:3000`, `env_file: .env`),
`mastra-postgres`, `vector` (שילוח לוגים ל-Axiom), וברשת `app_app-network`
המשותפת גם Strapi (`http://strapi:1337`), ה-socket-server ו-nginx.

**כלומר: אין מה להקים שרת חדש.** הבריף רץ בתוך הקונטיינר הקיים, והלוגים
שלו כבר נשלחים ל-Axiom דרך `vector` בלי עבודה נוספת.

## 3. ארכיטקטורת היעד

### 3.1 איפה זה רץ

```
systemd timer על ה-VPS   (digest.timer → digest.service)
   │  OnCalendar=*-*-* 07:30:00 Asia/Jerusalem
   │  curl -fsS -H "x-cron-secret: $CRON_SECRET" http://127.0.0.1:3000/api/digest
   ▼
sveltekit-api  (הקונטיינר הקיים)
   │
   ├─ audience()    → מי מקבל היום
   ├─ collect()     → לכל משתמש: qid 85levHubSummary + suggestions + מטלות
   ├─ whatsNew()    → דיף מול ה-cursor הקודם
   ├─ policy()      → ריק? מחוץ לחלון? מעל התקרה? → דלג
   ├─ compose()     → payload {he,en,ar} + deep-links
   ├─ deliver()     → mail | telegram | push | whatsapp
   └─ record()      → user-digest: lastSentAt, counts, cursor, status
   ▼
Strapi  (loopback, http://strapi:1337)
```

**למה systemd timer ולא Vercel cron:** אותם שיקולים שהוכרעו ב-TIMEGRAMA
§4.6 — אין תקציב זמן חתוך (סריקה של מאות משתמשים לא נכנסת ב-10 שניות),
המרחק ל-Strapi הוא loopback, ותדירות ותזמון בשליטתנו. הוסיפו לכך שכאן
התזמון **חייב** להיות מדויק לשעון ישראל, וזה בדיוק מה שקשה ב-Vercel cron
(שרץ ב-UTC ולא מבין שעון קיץ).

**דיוק שעון קיץ:** `OnCalendar` של systemd מכבד `Timezone=Asia/Jerusalem`
ביחידה, ולכן 07:30 נשאר 07:30 גם באוקטובר. `cron` רגיל על מכונה ב-UTC —
לא. אם בכל זאת נבחר cron, יש להריץ כל שעה עגולה ולתת ל-`policy.ts` להחליט
אם השעה המקומית היא שעת השליחה.

### 3.2 השכבות

```
src/lib/server/digest/
├── audience.ts       מי מקבל היום (סינון, עמודים, batching)
├── collect.ts        משיכת הנתונים הגולמיים לכל משתמש
├── whatsNew.ts       דיף מול הבריף הקודם  ← G3
├── compose.ts        פונקציה טהורה: נתונים → payload רב-לשוני
├── policy.ts         חלון שליחה, תקרה, ריק, העדפות משתמש  ← בעקבות emailPolicy.ts
├── deliver.ts        בחירת ערוץ + fallback
├── record.ts         כתיבה ל-user-digest
├── run.ts            התזמורת: for-each-user, batching, סיכום ריצה
└── *.test.ts         טסטים — compose/policy/whatsNew הן טהורות ובדיקות
```

**עיקרון:** `compose.ts`, `policy.ts` ו-`whatsNew.ts` הן **פונקציות
טהורות** בלי גישה לרשת — בדיוק כמו `src/lib/revenue/` ו-`src/lib/stipend/`.
כל ה-I/O נמצא ב-`collect`, `deliver`, `record`. זה מה שהופך את הבריף
לניתן לבדיקה בלי לשלוח מייל.

### 3.3 מודל הנתונים החדש — `user-digest`

קולקציה אחת ב-Strapi. **אחת בלבד**, ולא רשומה לכל שליחה: זו טבלת מצב, לא
לוג. הלוג נמצא ב-Axiom.

| שדה | טיפוס | תפקיד |
|---|---|---|
| `users_permissions_user` | relation (oneToOne) | הבעלים |
| `lastSentAt` | DateTime | מתי נשלח בריף אחרון בפועל |
| `lastRunAt` | DateTime | מתי נבדק לאחרונה (גם אם לא נשלח) |
| `cursor` | DateTime | קו הבסיס ל"מה חדש" — ר׳ §4.4 |
| `channels` | JSON | `{ mail: true, telegram: true, push: false, whatsapp: false }` |
| `frequency` | Enum | `daily \| weekly \| off` (**null = legacy = `daily`**) |
| `lastCounts` | JSON | הספירות של הבריף האחרון — לזיהוי "אין שינוי" |
| `status` | Enum | `ok \| skipped \| failed` |
| `lastError` | Text | הודעת השגיאה האחרונה |
| `attempts` | Integer | ניסיונות רצופים שנכשלו |
| `unsubToken` | UID | טוקן חד-פעמי לקישור ההסרה  ← G7 |

> **כלל ה-null של הפרויקט חל גם כאן.** בדיוק כמו `lifecycle`
> (`PLAN_OBJECT_ARCHIVAL`) ו-`stipendPolicy` (`PLAN_STIPEND`): לכל
> המשתמשים הקיימים אין רשומת `user-digest`, ולכן **"אין רשומה" חייב
> להתפרש כברירת המחדל** ולא כ"מנוי מבוטל". כל פילטר צריך
> `or: [{ frequency: { null: true } }, { frequency: { ne: "off" } }]`.

**למה לא לוותר על הקולקציה ולסמוך על `updatedAt` של המשתמש** — כי אז אין
`cursor`, אין תקרה, ואין דרך לדעת אם הבריף של אתמול נכשל. הניסיון של
TIMEGRAMA היה חד-משמעי: *"timegrama שנכשל נראה בדיוק כמו timegrama
שממתין"*. אסור לחזור על זה.

### 3.4 ה-endpoint

`src/routes/api/digest/+server.js`

```
GET /api/digest                     — ריצה מלאה (דורש סוד)
GET /api/digest?dry=1               — חישוב בלבד, לא שולח, מחזיר JSON
GET /api/digest?uid=123&dry=1       — משתמש בודד: מה היה נשלח לו
GET /api/digest?uid=123&force=1     — שליחה כפויה (עוקף חלון ותקרה) — לבדיקות
```

`?dry=1` הוא **דרישה, לא נוחות**. זה בדיוק הכלי ש-TIMEGRAMA §4.5 חסר בו
("מה תקוע?"), והוא מה שיאפשר לראות את הבריף לפני שהוא נשלח ל-500 איש.

**אימות (G8):** header `x-cron-secret` שנבדק מול `CRON_SECRET` שב-`.env`
של השרת. אותו דפוס שכבר קיים בריפו ל-`x-strapi-gate` ול-`x-internal-secret`
(`src/lib/server/internalSecret.js`). בנוסף, nginx לא יפרסם את `/api/digest`
החוצה כלל — ה-timer קורא ל-`127.0.0.1:3000` ישירות.

> **תיקון אגב:** אותו שער בדיוק חסר ל-`/api/timegrama` ול-`/api/monthi`
> (TIMEGRAMA B10.2). כדאי לכתוב את המידלוור פעם אחת ולהחיל על שלושתם.
> ר׳ פריט **S1** ב-§10.

### 3.5 שאילתות חדשות (qids)

| qid מוצע | מה | הרשאה ב-`qidsAccess.js` |
|---|---|---|
| `290digestAudience` | משתמשים פעילים בעמודים, עם `email`, `lang`, `telegramId`, `noMail`, `machshirs`, ורלציית `user_digest` | `['serviceAdmin']` **בלבד** |
| `291digestState` | רשומות `user-digest` לקבוצת מזהים | `['serviceAdmin']` |
| `292upsertDigestState` | מוטציית כתיבה של המצב | `['serviceAdmin']` |
| `293digestWhatsNew` | ספירת פריטים שנוצרו אחרי ה-cursor בריקמות של המשתמש | `['serviceAdmin']` |
| `294digestMissionsAndTasks` | משימות פעילות + ה-`acts` שלהן, עם שמות ותאריכים (§4.2) | `['user', 'serviceAdmin']` |

**`serviceAdmin` בלבד — זו לא בירוקרטיה.** `290digestAudience` היא, מעצם
הגדרתה, שאילתת enumeration של כל המשתמשים באתר עם כתובות המייל שלהם. הערת
ה-header של `qidsAccess.js` אומרת שכל qid חייב סיווג מודע; זו השאילתה
המסוכנת ביותר שתיווסף לקובץ הזה, והיא חייבת להיות בלתי-נגישה ל-`user`
ול-`apiKey` כאחד. גם הטסט `qidsAccess.test.ts` יאכוף שהיא מסווגת.

לשאילתות הקיימות (`85levHubSummary`, `209levMatchSuggestions`,
`212levResourceMatchSuggestions`) אין צורך בשינוי — הן כבר מרשות
`serviceAdmin`.

`294digestMissionsAndTasks` היא היחידה החדשה שראוי לפתוח גם ל-`user`:
היא מסוננת ממילא למשתמש המבקש, ועמוד הלב יכול להרוויח ממנה כ-slice
נוסף ב-`levSliceRegistry` (שם `mtaha` כבר קיים).

## 4. תוכן הבריף — הגדרה מדויקת

הניסוח שהמשתמש ביקש, ומאיפה כל מספר נשלף:

### 4.1 "כך וכך הצבעות שלא הגבת להן" — ⭐ הראשי

**המקור:** `processHubSummary` → `kpi.votes` ו-`kpi.urgent`, ו-`topFive`.

**למה זה ראשון:** זה הפריט היחיד בבריף שיש לו **מחיר לשתיקה**. לפי
על-העיקרון *"שתיקה היא הסכמה, בקצב הריקמה"*, אי-תגובה עד פקיעת ה-`restime`
היא **אישור**. `TIMEGRAMA_REMINDERS.md` מתעד את המקרה החי:

> `tosplit#10` הבשיל חוב של 217.4 על חבר ששתק 306 יום — הוא מעולם לא קיבל
> תזכורת אחת.

הבריף היומי הוא, מבחינה זו, **התיקון המערכתי ל-R4**. שני הפריטים חייבים
להיבנות יחד, אחרת ישלחו שתי הודעות על אותה הצבעה.

**הניסוח:** אף פעם לא "אתה חייב להצביע", תמיד "יש הצבעה שממתינה לך, ואם
לא תגיב עד TIME — הגרסה שעל השולחן תאושר". השקיפות הזו היא לא נימוס, היא
מה שהופך את "שתיקה היא הסכמה" להוגנת.

**דגל דחיפות:** פריט עם `urgent: true` (פחות מ-24 שעות ל-`timegrama.date`)
מקבל שורה נפרדת בראש: `🔴 X הצבעות נסגרות היום`.

### 4.2 "x משימות ממתינות שתבצע"

**המקור:** `mesimabetahaliches` — משימות בתהליך שהמשתמש לקח על עצמו,
מסוננות `forappruval: false, finnished: false` ו-`lifecycle` שאינו `archived`.

> **⚠️ שים לב — כאן נגמר מה שקיים.** qid `85levHubSummary` אמנם שולף את
> `mesimabetahaliches` באותו פילטר בדיוק, אבל **מחזיר `{ data { id } }`
> בלבד** — כלומר מספר, בלי שם, בלי טיימר, בלי `acts`. עמוד ה-hub באמת
> צריך רק את הספירה (`kpi.suggestions`), אבל **הבריף צריך שמות ותאריכים**.
> הפרטים המלאים קיימים רק ב-qid `83levMainUserQuery` — שהוא שאילתת עמוד
> הלב כולה, אלפי שורות, ויקר מדי להריץ פר-משתמש בלולאה.
>
> **המסקנה:** צריך qid חדש וצר — `294digestMissionsAndTasks` — שמחזיר
> לכל `mesimabetahalich` פעיל את `name`, `project.projectName`, `timer`,
> `hoursassinged`, `howmanyhoursalready`, `updatedAt`, ואת `acts` עם
> `shem`, `naasa`, `dateF`, `dateS`, `hashivut`. **אין קיצור דרך כאן.**

**מה ראוי לסנן החוצה:** משימה עם טיימר רץ אינה "ממתינה" — היא בעבודה
עכשיו. שווה לפצל לשתי שורות: *בעבודה* מול *ממתינות להתחלה*.

**קשר לרדימות:** משימה שעומדת בלי תנועה מעבר ל-`Project.dormancyDays`
תיפתח לה הצעת שחרור אוטומטית (`PLAN_OBJECT_ARCHIVAL`). הבריף הוא המקום
הנכון להזהיר **לפני** כן: *"המשימה X לא זזה 12 ימים; אחרי 14 תיפתח הצעת
שחרור"*. זו התראה ששום מקום אחר במערכת לא נותן.

### 4.3 "y מטלות"

**המקור:** `mesimabetahaliches[].acts` דרך אותו qid חדש של §4.2 — ישות
`Act` (`contentTypes.d.ts:1108`) עם `naasa: Boolean` (בוצע), `dateF`/`dateS`
(תאריכי יעד), `hashivut` (חשיבות), `myIshur`/`valiIshur` (אישורים).

**החישוב:** `acts` שבהן `naasa !== true`. שתי תת-שורות:
- מטלות שעבר להן `dateF` → **באיחור**.
- מטלות שה-`dateF` שלהן היום או מחר → **להיום**.

זו ההבחנה שהופכת את המספר לשימושי; "17 מטלות פתוחות" הוא רעש.

### 4.4 "z חדשים וחדשות" — הפער האמיתי (G3)

זו השורה היחידה שדורשת המצאה, כי המערכת יודעת מה **פתוח** ולא מה **חדש**.

**המנגנון: `cursor`.** ב-`user-digest` נשמר `cursor` = חותמת הזמן של סוף
החלון שנספר בבריף הקודם. הבריף הבא סופר רק ישויות עם
`createdAt > cursor`. אחרי שליחה מוצלחת, `cursor` מתקדם ל-`now`.

**מה נספר כ"חדש" (ברירת מחדל):**

| זן | פילטר | הערה |
|---|---|---|
| משימות פתוחות חדשות בריקמות שלי | `open_missions.createdAt > cursor` | + `lifecycle` שאינו `archived` |
| משאבים פתוחים חדשים | `open_mashaabims.createdAt > cursor` | |
| חברים חדשים בריקמה | `project.user_1s` שנוספו | דורש שדה תאריך הצטרפות — ר׳ שאלה Q3 |
| הודעות פורום חדשות | `messages.createdAt > cursor` בפורומים שאני משתתף בהם | יש `forum_last_seens` על המשתמש — **עדיף לנצל אותו במקום cursor** |
| מכירות חדשות בריקמה | `sales.createdAt > cursor` | ר׳ אזהרת ה-`holderStatus` למטה |
| מוצרים חדשים | `matanots.createdAt > cursor` | |

> **⚠️ אזהרת נכונות — מכירות.** לפי על-העיקרון של הסכמת מחזיק הכסף
> (`PLAN_sale_holder_consent`), מכירה נספרת רק כשהיא **effective**
> (`holderStatus` הוא `self` / `confirmed` / null-legacy) — **לעולם לא
> בזמן `open`**. בריף שמדווח "נכנסו 3 מכירות" כשאחת מהן היא טענה שהמחזיק
> עוד לא אישר — מדווח על מצבו הכספי של אדם אחר לפני שהוא הסכים. זה לא
> באג תצוגה, זו הפרה של העיקרון.

**כשה-`cursor` ריק (משתמש חדש, בריף ראשון):** להתייחס כאילו `cursor = now - 24h`
ולא לספור אחורה לנצח. בריף ראשון שמכריז "מצטרפים 412 פריטים חדשים" הוא
חסר ערך.

### 4.5 "כך וכך הצעות למשימות או להשקעת משאבים"

**המקור:** קולקציית `match-suggestion` — כבר מחושבת מראש בצד השרת
(`PLAN_MATCH_SUGGESTIONS`). שאילתות: `209levMatchSuggestions` (משימות),
`212levResourceMatchSuggestions` (משאבים). לספור `status !== 'dismissed'`,
ולהציג את ה-2–3 בעלי ה-`score` הגבוה ביותר.

> **⚠️ חפיפה שחייבת להיפתר לפני ההשקה.** מנוע ההתאמות **כבר שולח מייל
> "יש הצעה חדשה"** (`matching/notify.ts`), עד 3 ביום
> (`MAX_SUGGESTION_EMAILS_PER_USER_PER_DAY`). בלי הכרעה, משתמש יקבל את
> אותה הצעה פעמיים.
>
> **ההמלצה:** להוריד את המייל המיידי ל-**דחוף בלבד** (score גבוה מסף, או
> הצעה עם דדליין קרוב), ולתת לכל השאר להתגלגל לבריף היומי. זה גם מוריד
> את נפח המייל וגם משפר את חוויית ההצעות. זו הכרעת מוצר — **Q1** ב-§11.

### 4.6 הצורה הסופית של ה-payload

```ts
export interface DigestPayload {
  userId: string;
  lang: 'he' | 'en' | 'ar';
  username: string;
  generatedAt: string;
  isEmpty: boolean;              // ← אם true, לא נשלח כלום
  sections: {
    votes:       { count: number; urgent: number; items: DigestItem[] };
    missions:    { active: number; waiting: number; dormantSoon: DigestItem[] };
    tasks:       { open: number; overdue: number; dueToday: number };
    whatsNew:    { total: number; byKind: Record<string, number> };
    suggestions: { count: number; top: DigestItem[] };
  };
  cta: { url: string; label: { he: string; en: string; ar: string } };
}

export interface DigestItem {
  id: string;
  kind: string;                  // ערך ה-ani של כרטיס הלב
  title: string;
  projectName: string;
  deadline: string | null;
  urgent: boolean;
  url: string;                   // /lev?focus=<kind>&project=<pid>
}
```

**כללי i18n (חובה):** ה-payload נבנה **פר-נמען לפי `user.lang`**. זה בדיוק
המקרה היחיד שבו אובייקט `{he, en, ar}` הוא נכון ולא רגרסיה — CLAUDE.md
מציין את "server notification payloads" במפורש כיוצא מן הכלל, כי `$t()`
לא יכול לבטא "בשפת הנמען, בשרת, בלי דפדפן". **בכל זאת** — כשמופיע רכיב UI
(עמוד ההעדפות, עמוד ההסרה) הוא חוזר ל-`$t()` רגיל.

**אינטרפולציה:** בטקסטים של הבריף להשתמש ב-`{{count}}` ולא ב-`{{n}}` —
placeholder באורך תו אחד לא נתפס ברג׳קס של המנתח ומרונדר כמחרוזת ריקה
(CLAUDE.md, סעיף i18n, מקרה 4). זו תקלה שאף בדיקה חוץ מ-`npm run check:i18n`
לא תופסת.

## 5. מדיניות — מה הופך בריף לבריף ולא לספאם

`src/lib/server/digest/policy.ts`, בעקבות `matching/emailPolicy.ts`.

### 5.1 חמשת הכללים

1. **בריף ריק לא נשלח.** `isEmpty === true` ⇒ דלג, רשום `status: 'skipped'`.
   זה הכלל החשוב ביותר במסמך. משתמש שמקבל "0 הצבעות, 0 משימות, 0 חדשות"
   לומד תוך שבוע להתעלם מהשולח.
2. **אחד ביום, לכל היותר.** `lastSentAt` בתוך 20 השעות האחרונות ⇒ דלג.
   (20 ולא 24, כדי שריצה שאיחרה בחצי שעה לא תדלג על יום שלם.)
3. **חלון שליחה.** ברירת מחדל 07:00–09:00 שעון ישראל. מחוץ לחלון —
   לא נשלח, **ולא נצבר לתור**; בדיוק כמו `isWithinSendWindow` בקיים.
4. **"אין שינוי" נחשב ריק.** אם `lastCounts` זהה לספירות הנוכחיות ואין
   `whatsNew`, אין מה לספר. מונע "3 הצבעות ממתינות" 14 בקרים ברצף.
   **חריג:** פריט שהפך ל-`urgent` מאז אתמול הוא כן שינוי, גם אם המספר זהה.
5. **המשתמש שולט.** `frequency: 'off'` ⇒ לא נשלח. `noMail: true` מכבה את
   ערוץ המייל בלבד ולא את הבריף כולו (אם יש לו טלגרם).

### 5.2 העדפות משתמש (G6)

מקומן הטבעי הוא `src/lib/components/userPr/editBasic.svelte`, שכבר מנהל
`lang`, `noMail` וקישור הטלגרם — כלומר יש שם כבר טופס העדפות התראה עובד,
ורק צריך להוסיף לו קטע:

- **תדירות:** יומי · שבועי (ראשון בבוקר) · כבוי.
- **ערוץ:** מייל · טלגרם · פוש · ווצאפ (§7) — ריבוי בחירה.
- **שעה:** אופציונלי, ברירת מחדל 07:30.

### 5.3 קישור הסרה (G7)

כל מייל בריף חייב `List-Unsubscribe` בכותרות **וקישור גלוי בגוף**:
`https://www.1lev1.com/unsub?t=<unsubToken>`. הטוקן הוא UID אקראי
מ-`user-digest` — **לעולם לא מזהה המשתמש ולא המייל בכתובת ה-URL**, כי
כתובת כזו דולפת דרך ה-Referer ודרך לוגים.

עמוד ההסרה מציע שלוש דרגות ולא כפתור אחד, בעקבות על-העיקרון "אין 'לא'
מוחלט": *עבור לשבועי* · *רק הצבעות דחופות* · *הפסק לגמרי*.

## 6. ערוצי שליחה

### 6.1 מייל — קיים, צריך תבנית ותשתית שליחה מרוכזת

**מה עובד:** `EmailService` → `/api/sendMail` → `mailer.js` (Zoho, pool
אחד, `rateLimit: 20/min`, `sendMailSafe` שלא זורק לעולם).

**מה חסר:**

- **`src/lib/components/mail/dailyDigest.svelte`** — תבנית svelty-email
  מרובת סעיפים. כל סעיף מוסתר כשהספירה 0. RTL לעברית ולערבית.
- **⚠️ צוואר הבקבוק האמיתי: 20 מיילים לדקה.** 500 משתמשים = **25 דקות**
  של שליחה רצופה. זה עדיין בסדר לבריף בוקר (הריצה מתחילה 07:30 ומסתיימת
  07:55), אבל **לא ישתרע**. ההערה ב-`mailer.js` מסבירה למה המגבלה שם:
  Zoho קרא ל-churn של חיבורים *"Unusual sending activity"* וחסם את כל
  החשבון `notifications@`. **אסור להעלות את המגבלה בלי לבדוק את מכסת Zoho.**
  התכנית: לבנות נכון עכשיו, ולפתוח את **Q4** (מעבר לספק דיוור ייעודי)
  כשעוברים ~1,000 משתמשים.
- **`List-Unsubscribe` + `List-Unsubscribe-Post`** ב-`mailer.js` — פרמטרים
  אופציונליים ל-`sendMailSafe`.
- **טיפול ב-bounce:** כרגע כתובת פסולה נרשמת ללוג ונשכחת. מינימום: אחרי
  3 כישלונות רצופים (`attempts >= 3` ב-`user-digest`) לכבות את ערוץ המייל
  למשתמש הזה אוטומטית ולרשום `lastError`.

### 6.2 טלגרם — קיים, צריך התאמה לשליחה מרוכזת (G10)

**מה עובד:** `TelegramService` → `/api/ste` → Telegraf, HTML,
כפתור inline. הקישור נקבע ב-`/api/newTelegram`.

**מה חסר:**

1. **לא לצאת החוצה.** `TelegramService.sendToUser` פונה ל-
   `https://www.1lev1.com/api/ste` — כלומר מה-VPS ל-Vercel ובחזרה ל-API
   של טלגרם. לבריף צריך `sendTelegramDirect()` שקורא ל-Telegram Bot API
   ישירות מה-VPS. חוסך קפיצה, מסיר תלות ב-Vercel, ומאפשר טיפול בשגיאות.
2. **מגבלת קצב.** טלגרם מרשה ~30 הודעות לשנייה לבוט, וחוסם עם `429` ועם
   `retry_after`. צריך תור עם ~25/שנייה וכיבוד `retry_after`. כרגע
   `/api/ste` עושה `.catch(err => console.error(...))` — כלומר **בולע את
   ה-429 בשקט**, וההודעה נעלמת בלי עקבות.
3. **משתמש שחסם את הבוט.** טלגרם מחזיר `403: bot was blocked by the user`.
   זה קבוע, לא זמני — לנקות את `telegramId` (או לסמן `channels.telegram: false`)
   ולא לנסות שוב לנצח.
4. **הבריף ארוך מהתראה.** מגבלת הודעה היא 4096 תווים. הבריף צריך להיות
   HTML קצר עם 2–4 כפתורי deep-link (`הצבעות` · `משימות` · `הצעות`)
   במקום כפתור אחד גנרי.
5. **`parse_mode: HTML` ותווי בקרה.** שם ריקמה שמכיל `<` או `&` ישבור את
   ההודעה. צריך escaping — זו בדיוק תקלה B5 של TIMEGRAMA באצטלה אחרת.

**יתרון הטלגרם לבריף:** אין מגבלת קצב מעשית (25/שנייה = 500 משתמשים
ב-20 שניות), אין ספאם-פילטר, ההודעה מגיעה לנייד, וכפתורי ה-deep-link
עובדים. **זה הערוץ המועדף, והמייל הוא ה-fallback.**

### 6.3 פוש — קיים חלקית

`PushService` שולח למכשירים הרשומים (`machshirs`). לבריף הוא מתאים רק
כשורה אחת: *"3 הצבעות ממתינות לך"* + לחיצה שפותחת את `/lev?focus=votes`.
פוש אינו יכול לשאת בריף מלא. **תפקידו: תזכורת, לא תוכן.**

### 6.4 בחירת הערוץ ו-fallback

```
לכל משתמש:
  channels = user-digest.channels  ||  ברירת המחדל שנגזרת מהמצב:
      telegramId קיים          → telegram
      noMail !== true          → mail
      machshirs.length > 0     → push (תזכורת בלבד)

  שלח לכל הערוצים הפעילים במקביל (Promise.allSettled)
  אם כולם נכשלו → status:'failed', attempts++
```

**כלל:** ריבוי ערוצים הוא בחירה של המשתמש, לא ברירת מחדל. אדם שקיבל את
אותו בריף במייל **וגם** בטלגרם **וגם** בפוש מרגיש נרדף. ברירת המחדל
לפני שהמשתמש בחר: **ערוץ אחד** — טלגרם אם מקושר, אחרת מייל.

## 7. ווצאפ — במה זה כרוך

זהו הסעיף היחיד שמדבר על משהו שאינו קיים בשום צורה בריפו. הוא ארוך מפני
שהעלות האמיתית של ווצאפ אינה בקוד.

### 7.1 העובדה שקובעת הכול

**ווצאפ אינו טלגרם.** בטלגרם פותחים בוט בחמש דקות, ומרגע שהמשתמש לחץ
`/start` אפשר לשלוח לו מה שרוצים, מתי שרוצים, בחינם. בווצאפ:

1. צריך **חשבון עסקי מאומת** מול Meta.
2. אפשר לשלוח ביוזמת המערכת **רק תבנית שאושרה מראש** על ידי Meta.
3. **כל הודעה עולה כסף.**
4. שליחה בלי opt-in מתועד = חסימת המספר.

הבריף היומי הוא, בהגדרה, הודעה **ביוזמת המערכת** — ולכן הוא נופל בדיוק
בקטגוריה היקרה והמפוקחת ביותר. אין דרך לעקוף את זה.

### 7.2 שלוש דרכים, ובחירה אחת

| דרך | מה זה | המלצה |
|---|---|---|
| **WhatsApp Cloud API** (ישירות מול Meta) | ה-API הרשמי, מתארח אצל Meta. הרשמה דרך Meta Business, webhook לקבלת הודעות, REST רגיל. | ✅ **זו הבחירה.** בלי מתווך, בלי תוספת מחיר, בקרה מלאה. |
| **BSP** (Twilio / 360dialog / Vonage / MessageBird) | ספק מורשה שעוטף את אותו API. מקצר את האונבורדינג ואת אישור התבניות. | חלופה סבירה אם האימות מול Meta נתקע. עולה יותר לכל הודעה. |
| **ספריות לא רשמיות** (`whatsapp-web.js`, Baileys) | מריצות סשן ווצאפ-ווב אמיתי בשרת. | ❌ **לא.** הפרת תנאי שימוש, המספר נחסם ללא התראה ובלי ערעור, הסשן נופל בכל עדכון, וזה מספר טלפון אמיתי שאובד. לא מתאים לשום מערכת ייצור. |

### 7.3 מה נדרש כדי להתחיל — הרשימה המלאה

**א. חשבונות ואימות (ימים עד שבועות, לא שעות):**

1. **Meta Business Account** — אם אין, להקים.
2. **Business Verification** — Meta דורשת מסמכי התאגדות ואימות דומיין.
   זה החלק הארוך; לתכנן שבוע עד שלושה.
3. **WhatsApp Business Account (WABA)** בתוך ה-Business Manager.
4. **מספר טלפון ייעודי** שאינו רשום כרגע לווצאפ רגיל או עסקי. אזהרה: אם
   מעבירים מספר קיים — הוא מפסיק לעבוד באפליקציה. **לרכוש מספר חדש.**
5. **Display Name** לאישור Meta. חייב להתאים לשם העסק; `1lev1` צריך
   להיות מקושר לישות משפטית מזוהה.
6. **System User + טוקן קבוע** (טוקן זמני פג אחרי 24 שעות — טעות אונבורדינג
   קלאסית).

**ב. תבניות הודעה (Message Templates) — הליבה:**

מחוץ ל"חלון השירות" בן 24 השעות (שנפתח רק כשהמשתמש כותב **אלינו**), מותר
לשלוח **אך ורק תבנית מאושרת**. הבריף היומי תמיד מחוץ לחלון.

- **קטגוריה:** `UTILITY`. הבריף הוא עדכון תפעולי על חשבון קיים, לא שיווק.
  סיווג שגוי כ-`MARKETING` יקר יותר ונחסם יותר.
- **תוכן קבוע + משתנים:** גוף התבנית קבוע; רק `{{1}}`, `{{2}}`… משתנים.
  כלומר **אי אפשר לשלוח את הבריף כטקסט חופשי.** הניסוח חייב להיות:

  > שלום {{1}}, יש לך {{2}} הצבעות שממתינות לתגובתך, {{3}} משימות פעילות
  > ו-{{4}} עדכונים חדשים ברקמות שלך.

  עם כפתור URL שמוביל ל-`1lev1.com/lev`.
- **אישור לכל שפה בנפרד.** he, en, ar = שלוש הגשות, כל אחת עם זמן אישור
  משלה (דקות עד 24 שעות) ועם אפשרות דחייה משלה.
- **דחייה קורית.** תבנית שנראית שיווקית בקטגוריית utility נדחית; צריך
  לתקן ולהגיש שוב.
- **שינוי בניסוח = הגשה מחדש.** אין deploy מהיר לטקסט של בריף בווצאפ.
  זו מגבלה מוצרית משמעותית לעומת מייל וטלגרם.
- **פרמטרים משתנים בלבד — לא רשימות.** אי אפשר לשלוח בווצאפ את
  "5 הפריטים הדחופים" כמו במייל. הווצאפ יישא **ספירות + קישור**, והתוכן
  המלא נשאר באתר. זו לא פשרה זמנית, זו התכונה של הערוץ.

**ג. הסכמה מפורשת (opt-in) — דרישת מדיניות, לא נימוס:**

Meta מחייבת opt-in מתועד לפני ההודעה הראשונה, ובודקת אותו בפועל דרך
"איכות" המספר. מה שצריך להיבנות:

1. שדה `whatsappPhone` על המשתמש + `whatsappOptInAt` (DateTime) +
   `whatsappOptInSource` (טקסט: מאיזה מסך ההסכמה ניתנה).
2. **אימות מספר ב-OTP** — לא לסמוך על הקלדה. שליחת קוד בווצאפ עצמו,
   והמשתמש מקליד אותו חזרה. זה גם מאמת בעלות וגם מוכיח opt-in.
3. טקסט הסכמה מפורש ליד השדה, ורישום שלו.
4. **`STOP` חייב לעבוד.** Webhook שמזהה `STOP` / `הפסק` / `ביטול`
   בהודעה נכנסת ומכבה מיידית את `channels.whatsapp`. בלי זה — דירוג
   האיכות של המספר יורד, ובסוף Meta מגבילה את קצב השליחה.

**ד. ציון איכות ומדרגות קצב:** Meta נותנת לכל מספר ציון איכות
(ירוק/צהוב/אדום) לפי חסימות ודיווחים של נמענים, ומדרגות שליחה יומיות
(1K → 10K → 100K) שעולות עם התנהגות טובה ו**יורדות** עם התנהגות רעה.
משמעות מעשית: **להתחיל עם קבוצה קטנה של מתנדבים**, לא לשגר ל-500 איש
ביום הראשון.

### 7.4 עלות

הדגש החשוב: **בטלגרם ובמייל השליחה חינם. בווצאפ כל בריף עולה.**

- Meta עברה (2025) מתמחור לפי שיחה (conversation) לתמחור **לכל הודעת
  תבנית**, לפי קטגוריה ולפי מדינת הנמען.
- קטגוריית `UTILITY` היא הזולה מבין תבניות היוזמה, וישראל אינה מהשווקים
  הזולים.
- הודעות **בתוך** חלון השירות (תשובה למשתמש שכתב אלינו) חינם.

**המשמעות המוצרית:** בריף יומי בווצאפ = **הודעה בתשלום לכל משתמש כל יום**.
בקנה מידה של 500 משתמשים זו הוצאה חודשית קבועה ולא זניחה. המסקנה:

> **ווצאפ צריך להיות אופציה שהמשתמש מבקש במפורש, לא ברירת מחדל.**
> ואולי אפילו — בשלב ראשון — רק לבריף **שבועי**, או רק להצבעות דחופות
> (`urgent > 0`), שם ערך ההודעה מצדיק את מחירה.

לפני ההחלטה יש לתמחר מול המחירון העדכני של Meta לישראל בקטגוריית utility
ולהכפיל במשתמשים × ימים. זה חישוב של חמש דקות ש**חייב** לקרות לפני שכותבים
שורת קוד — **Q5** ב-§11.

### 7.5 מה נבנה בקוד

```
src/lib/server/notifications/WhatsAppService.ts
   ├─ sendTemplate(phone, templateName, lang, params[])
   ├─ טיפול ב-rate limit ו-retry
   └─ מיפוי שגיאות: 131047 (חלון נסגר), 131026 (לא ניתן למסירה),
                     131049 (מוגבל באיכות), 470 (תבנית פגה)

src/routes/api/whatsapp/webhook/+server.js
   ├─ GET  — אימות ה-webhook מול Meta (hub.challenge)
   ├─ POST — הודעות נכנסות + סטטוסי מסירה (sent/delivered/read/failed)
   ├─ אימות חתימת X-Hub-Signature-256   ← חובה, לא אופציה
   └─ זיהוי STOP → כיבוי הערוץ

src/lib/server/notifications/whatsappTemplates.ts
   └─ שמות התבניות המאושרות + סדר הפרמטרים, במקום אחד

Strapi: whatsappPhone, whatsappOptInAt, whatsappOptInSource, whatsappStatus
UI:     קטע ווצאפ ב-editBasic.svelte + מסך אימות OTP
```

**אבטחה:** אימות `X-Hub-Signature-256` על כל POST ל-webhook הוא חובה
מוחלטת — בלי זה כל אחד באינטרנט יכול להזריק "הודעות נכנסות" מזויפות
ולפתוח חלון שירות בשם משתמש אחר. אותה משמעת בדיוק כמו `x-strapi-gate`
ו-`isInternalRequest` בקיים.

### 7.6 מה **לא** לעשות

- ❌ לא להשתמש ב-`whatsapp-web.js` / Baileys. המספר ייחסם.
- ❌ לא להפוך את ווצאפ לברירת מחדל.
- ❌ לא לחשוב שקישור `wa.me` (שכבר קיים ב-
  `src/lib/components/share/shareButtons/WhatsApp.svelte`) הוא פתרון —
  הוא **פותח את ווצאפ אצל המשתמש כדי שהוא ישלח**. ההפך המדויק מבריף.
- ❌ לא לשלוח לפני שהתבנית אושרה. הודעה בטקסט חופשי מחוץ לחלון פשוט נכשלת.

### 7.7 סיכום השקעה

| שלב | מאמץ | תלוי בנו? |
|---|---|---|
| חשבונות + אימות עסקי + מספר | 1–3 שבועות **המתנה** | ❌ Meta |
| אישור תבניות (3 שפות) | שעות עד ימים, פר-הגשה | ❌ Meta |
| `WhatsAppService` + webhook + חתימה | 2–3 ימי פיתוח | ✅ |
| opt-in + OTP + UI + שדות Strapi | 2–3 ימי פיתוח | ✅ |
| טיפול ב-STOP, איכות, מדרגות | 1 יום + תחזוקה מתמשכת | ✅ |
| **תפעול** | תשלום חודשי לכל הודעה | ✅ החלטה שלנו |

**המלצה: ווצאפ הוא שלב 6.** לא לחסום עליו את הבריף. הבריף עולה לאוויר
עם טלגרם ומייל — שניהם כבר בנויים — וווצאפ נכנס כערוץ נוסף אחרי שהתוכן
הוכיח את עצמו והתשתית האדמיניסטרטיבית מוכנה.

## 8. תצפית ומדידה

הלקח המרכזי של TIMEGRAMA: *"אין שום מדד, שום לוג מובנה, שום שדה שגיאה.
timegrama שנכשל נראה בדיוק כמו timegrama שממתין."* אסור לחזור על כך.

- **לוג מובנה לכל ריצה** — `[digest]` עם JSON אחד:
  `{ run, users, sent, skipped, failed, byChannel, durationMs }`.
  ה-`vector` שכבר רץ בקומפוז שולח את זה ל-Axiom בלי עבודה נוספת.
- **שדות סטטוס לכל משתמש** — `status`, `lastError`, `attempts` ב-`user-digest`.
- **`?dry=1`** — לראות מה היה נשלח, בלי לשלוח.
- **התראה לאדמין** — אם הריצה נכשלה לגמרי, או אם שיעור הכישלון עולה על
  20%: הודעת טלגרם לערוץ האדמין. `/api/cron` כבר עושה בדיוק את זה
  (`NEW_TELEGRAM` / `TELEGRAM_CHAT_ID`) — לחקות.
- **מדדים לעקוב אחריהם:** אחוז נשלח מתוך הקהל · אחוז בריפים ריקים (אם
  גבוה — הבריף לא רלוונטי לרוב) · הסרות ליום (אם עולה — הבריף מטריד) ·
  קליקים לפי ערוץ · **האם `votes` יורד** — זו המטרה האמיתית של הפרויקט.

## 12. מה במפורש **לא** נכנס

- **לא** מנוע תורים כללי. הבריף רץ פעם ביום, סינכרוני, בקצב הידוע מראש.
  Redis/BullMQ הם over-engineering ל-500 משתמשים על מכונה עם 1.9GB RAM.
- **לא** סיכום AI של הבריף בגרסה הראשונה. יש `@ai-sdk` בפרויקט, אבל
  ספירה נכונה עדיפה על ניסוח יפה, וטעות AI בבריף על כסף היא יקרה.
- **לא** התראות בזמן אמת. `SocketIOServer` כבר עושה את זה; הבריף הוא
  ההפך המכוון — **הצטברות**.
- **לא** בריף לפי ריקמה. הודעה אחת לאדם, על כל הריקמות שלו.
- **לא** SMS. עלות דומה לווצאפ בלי הכפתורים ובלי העיצוב.
