## 1. מה הפלטפורמות הגדולות נותנות, ומה לקחנו

נבדק מול Shopify (Shipping profiles + zones + rates עם תנאי משקל/מחיר, Local
delivery לפי רדיוס/מיקוד, Local pickup עם מיקומים), WooCommerce (אזורים מסודרים —
הראשון שמתאים קובע, מיקודים, flat rate עם עלות לפריט, shipping classes, משלוח
חינם מעל סכום) וחנויות ישראליות (עיר/נפה, ימי חלוקה לאזור, דירה/קומה/כניסה, נקודות איסוף).

| יכולת | אצלנו |
|---|---|
| אזורים לפי מדינה / מחוז / מיקוד | ✅ מדינה (ISO), **נפה** (לפי רשימת הלמ"ס), **יישוב**, תחילת מיקוד, "כל השאר" |
| סדר אזורים — הראשון שמתאים קובע | ✅ חצים למעלה/למטה בלשונית |
| כמה שיטות לאזור (שליח / דואר / אקספרס) | ✅ עד 10 לאזור, ממוינות מהזולה |
| מחיר קבוע, תוספת לפריט נוסף, לפי ק"ג | ✅ `fee`, `perItem`, `perKg` |
| מדרגות לפי סכום או משקל | ✅ `tiersBy` + `tiers` |
| משלוח חינם מעל סכום + "עוד X למשלוח חינם" | ✅ `freeOver`, ובעגלה `freeOverRemaining` |
| מינימום הזמנה לשיטה, משקל מרבי | ✅ `minSubtotal`, `maxWeightKg` |
| זמן הגעה, זמן הכנה | ✅ `etaMinDays/etaMaxDays`, `handlingDays` (ימי עבודה א׳–ה׳) |
| ימי חלוקה לאזור ("צפון בימי שלישי") | ✅ `days` + "יוצא ב…" מחושב לפי שעון ישראל |
| איסוף עצמי עם כתובת ושעות | ✅ נקודות איסוף ברמת הרקמה, לא תלויות בכתובת |
| מחלקות משלוח (מוצר גדול/מיוחד) | ✅ כלל למוצר: איסוף בלבד / משלוח בלבד / דיגיטלי, תוספת ליחידה, משקל |
| כתובת ישראלית מלאה + השלמה אוטומטית | ✅ יישוב ורחוב מהמאגר הממשלתי, מספר, דירה, קומה, כניסה, מיקוד, הערות לשליח |
| כתובת שאף אזור לא מכסה | ✅ "נתאם איתכם" (ניתן לכיבוי) — לא חוסמים הזמנה |
| **לא עכשיו:** חישוב חי מחברת שילוח (API של HFD/צ'יטה/דואר), רדיוס מק"מ, בחירת חלון שעות, תוויות משלוח, מע"מ על משלוח | §9 |

## 2. המודל — `Project.shipping` (JSON)

הקוד: `src/lib/shop/shipping.ts` (טהור, משותף לשרת ולתצוגה המקדימה בלשונית; 25 בדיקות).

```
ShippingConfig { enabled, handlingDays, contactFallback,
  zones: [{ id, name, everywhere, countries[], districts[], cities[], postalPrefixes[],
            methods: [{ id, name, fee, perItem, perKg, tiersBy, tiers[], freeOver,
                        minSubtotal, maxWeightKg, etaMinDays, etaMaxDays, days[], note }] }],
  pickupPoints: [{ id, name, city, address, hours, note, fee }],
  products: [{ productId, kinds|null, surcharge, weightGrams }],
  updatedAt, updatedBy }
```

- **מזהי אפשרות** שהקונה בוחר ומדווח בהזמנה: `m:<zone>:<method>`, `p:<point>`, `digital`, `contact`.
- **עמלות במטבע הרקמה.** `normalizeShippingConfig` לא סומך על מה שנשמר; אזור ריק / בלי שם נחסם בשמירה (`configProblems`).
- **מוצר מצמצם את הדרכים**: הכלל בלשונית, אחרת סוגי `deliveryOptions` של המוצר; עגלה עם מוצר "איסוף בלבד" לא מקבלת שיטות משלוח (`noDeliveryProducts` אומר למה).
- **תוספת למוצר נשארת גם כשהמשלוח חינם**; `freeOver` מאפס רק את מחיר השיטה.
- **משקל**: הווריאנט (`ProductVariant.weightGrams`, קיים) ואחרת הכלל למוצר; משקל לא ידוע = 0 ומסומן `weightUnknown` כשיש שיטה לפי משקל.

## 3. יישובים, נפות ורחובות — `src/lib/server/places/israel.ts`

רשימת היישובים (`5c78e9fa-…`, כולל `שם_נפה`) והרחובות (`9ad3862c-…`) מ-data.gov.il,
במטמון יום לכל מופע שרת. הנפה **נגזרת בשרת מהעיר** — אף פעם לא נלקחת מהקונה —
כך שאזור "נפת חיפה" מכסה כל יישוב בה בלי לרשום אותם. data.gov.il לא עונה ⇒
אין השלמה, אבל אזור לפי שם יישוב עדיין תופס (השוואה סלחנית: "תל-אביב" = "תל אביב - יפו").

## 4. API

| קריאה | מה |
|---|---|
| `GET /api/v1/r/{rikma}/shipping` | האזורים, המחירים, נקודות האיסוף, `freeOver` הנמוך — מה שמראים לפני שיש כתובת |
| `POST /api/v1/r/{rikma}/shipping/quote` | `{ lines:[{productId,variantId,quantity,unitPrice}], address:{country,city,zip} }` ⇒ כל אפשרות עם מחיר, אזור, זמן, יום יציאה. `configured:false` ⇒ התבנית נשארת עם אפשרויות המוצרים |
| `GET /api/v1/places/cities[?q=]` | כל היישובים + נפות (בלי `q`, לסינון בדפדפן) או התאמות |
| `GET /api/v1/places/streets?city=<code>[&q=]` | רחובות יישוב |

אותו סדר בדיקות של הקטלוג (`startShippingRoute`): מפתח, רקמה, התאמת מפתח↔נתיב, קיום.
עד ש-`1.0b` נפרס, `shippingSchemaLive` עונה "לא" והכול מתנהג כמו לפני.

## 5. ההזמנה

- `POST /orders` מקבל `delivery.optionId`; הכתובת היא שק שטוח (`city, street, house, apartment, floor, entrance, zip, country, notes`).
- `createPaidOrder` **מתמחר שוב** (`shippingRecordOf`) וכותב `Order.shipping` (שיטה, אזור, נקודת איסוף, `fee` שנגבה מול `quotedFee`, זמן, יום יציאה) — בכתיבה נפרדת אחרי יצירת השורה, כך שהזמנה לעולם לא נכשלת בגללו.
- **פער במחיר הוא הערה, לא סירוב** — הקונה כבר שילם. ההערה בהזמנה אומרת מה נגבה ומה ההגדרות אומרות.
- מסך ההזמנה ותעודת המשלוח מציגים שיטה/אזור/איסוף, דמי משלוח, זמן, יום יציאה, ודירה/קומה/כניסה.

## 6. בניהול המכירות — לשונית "משלוחים"

`/moach/[pid]/sales/manage/shipping`: הפעלה, ימי הכנה, "נתאם איתכם"; אזורים
(כיסוי: מדינות, נפות כצ'יפים, יישובים עם השלמה, מיקודים; שיטות עם "עוד אפשרויות");
נקודות איסוף; כללי מוצרים; **בדיקה חיה** — יישוב/סכום/פריטים/משקל ⇒ מה קונה יראה,
באותה פונקציה שהשרת מתמחר בה. שמירה אחת לכל הטיוטה (`saveShippingConfig`).

**הקישור לאופן שבו 1lev1 עובד:** הלשונית לא מחליטה מי מוציא את החבילה. כלל ביצוע
(`saveFulfillmentStep`) יכול עכשיו להצטמצם ל**אזורים** (`when.shippingZones`) —
"הזמנות לצפון פותחות מטלה למשלוחן של הצפון" — ונוחת על מי שמחזיק את המשימה, עם
ההסכמה שלו/ה כמו כל כלל (עקרון 3 של PLAN_SHOP_OPERATIONS). כרטיס האזור מראה אילו כללים
מוציאים אליו ומקשר ללשונית הביצוע. מחירי המשלוח עצמם לא מזיזים חלק של אף אחד, ולכן
כל חבר שומר אותם ישירות (כמו "נשלח"); מי שמר ומתי — על ההגדרות.

## 7. התבנית (`1lev1-shop-starter`)

- עגלה: טופס "לאן לשלוח" (מדינה מתוך מדינות האזורים, יישוב ורחוב עם השלמה מ-`/api/places`, מספר, דירה, קומה, כניסה, מיקוד, הערות לשליח). כל שינוי עיר/מיקוד/מדינה ⇒ הצעת מחיר חדשה מ-1lev1. אפשרויות עם זמן, יום יציאה, כתובת ושעות איסוף, "עוד X למשלוח חינם".
- **התבנית לא מחשבת משלוח בעצמה.** לפני תשלום (`checkoutDelivery`) — הצעה חדשה עם הכתובת; מחיר שזז ⇒ 409 והעגלה חוזרת לקונה; משלוח בלי כתובת מלאה ⇒ 400 לפני דף התשלום.
- Stripe: הכתובת ב-metadata ובלי טופס כתובת שני; PayPal: `SET_PROVIDED_ADDRESS`. ה-webhook מדווח `optionId` + הכתובת. תוקן גם `postalCode` ⇒ `zip` (1lev1 קורא `zip`).
- עמוד מוצר: "משלוח חינם מעל X" ונקודות האיסוף כשהרקמה עובדת עם אזורים.
- רקמה בלי אזורים — הכול כמו קודם (`delivery[]` של המוצרים).

## 8. פריסה, ומה לא נבדק

**סדר:** `1.0b` (שני שדות JSON; להוסיף הרשאות אין צורך — אין collection חדש) ⇒ `npm run types:update` ב-`1.0main` (הוספתי את השדות ידנית לקבצים המיוצרים, כמו ש-codegen היה מוסיף) ⇒ `1.0main` ⇒ התבנית.

**נבדק:** 25 בדיקות לליבה, 6 לרישום בהזמנה ולמאגר היישובים, כלל אזור במנוע הביצוע, `validate:qids`, `check:i18n`, `check:script`, `check:proxy`, svelte-check נקי בקבצים החדשים. בתבנית: 61 בדיקות, svelte-check, `vite build`, ובדפדפן מול mock בצורת ה-API שמתמחר בפונקציה האמיתית — לפני כתובת רק איסוף; רמת גן ⇒ שליח 30 ₪ ו"עוד 115 ₪ למשלוח חינם"; נהריה ⇒ "הצפון" דרך נפת עכו עם יום יציאה; חסר מספר בית ⇒ נחסם לפני שליחה; הזמנה בתיאום הגיעה עם כתובת מלאה, `fee:30`, `optionId` — והגוף **עבר את `validateOrderPayload` האמיתי** ותומחר זהה בצד 1lev1. 375px בלי גלילה אופקית.

**לא נבדק:** לשונית "משלוחים" בדפדפן (צריך את הסכמה פרוסה — עד אז היא מציגה "עוד לא זמין"), שמירה מול Strapi אמיתי, `Order.shipping` נכתב ונקרא, Stripe/PayPal אמיתיים עם הכתובת.

## 9. פתוח / המשך

1. **כלי MCP** לחנות (`getShippingConfig`, `quoteShipping`) — כדי שהעוזר יענה "כמה עולה משלוח לחיפה".
2. **ספקי שילוח** (HFD, צ'יטה, דואר ישראל): מחיר חי + תווית — מתאם לשיטה (`carrier`), כמו מתאמי התשלום.
3. רדיוס מק"מ מנקודת האיסוף (צריך geocoding), חלונות שעה למשלוח, מע"מ על משלוח לעוסק מורשה.
4. האם שינוי מחירי משלוח ברקמה גדולה צריך הסכמה (כמו מחיר מוצר) — היום חבר שומר ישירות.
