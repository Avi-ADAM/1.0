## 1. 🔴 חמור — כל שאילתות הצ׳אט/פורומים נכשלות ב‑403 בפרודקשן

**מופיע בכל עמוד של משתמש מחובר.** בכל טעינת עמוד (`/lev`, `/me`, `/hub`,
`/moach`, `/project`, `/gift`, `/demand`, `/consensus`, `/availableMission`,
`/availiableResorce`, `/onboard/*`) נשלחת בקשה שנכשלת:

```
POST https://www.1lev1.com/api/send  →  403
  request : {"data":{"query":"{\n usersPermissionsUser (id:256) {data{ attributes{ …"}}
  response: {"message":"Raw GraphQL queries are not allowed; use a queId"}
  console : [SocketClient] Authentication failed / Failed to load resource: 403
```

**הסיבה:** `src/lib/stores/pendMisMes.js:82` ו‑`:159` — הפונקציה `initialForum()`
בונה מחרוזת GraphQL גולמית ומעבירה אותה ל‑`SendTo(que)`. שני הענפים
(`all === true` וגם `all === false`) שולחים raw query, בלי `queId`.

`src/routes/api/send/+server.js:80` חוסם raw queries מחוץ ל‑dev:

```js
} else {
    if (!isDev) throw error(403, 'Raw GraphQL queries are not allowed; use a queId');
```

**המשמעות:** כל הנתונים ש‑`initialForum` אמור להביא — שם המשתמש, תמונת
הפרופיל הגלובלית (`uPic`), רשימת הרקמות (`userProjects`), וכל הפורומים
וההודעות של המשתמש (כולל פורומי חלוקות) — **אף פעם לא מגיעים בפרודקשן**.
מערכת הצ׳אט של המשתמש המחובר לא עובדת כלל. בדב זה עובד, ולכן זה לא נתפס.

**התיקון:** להוסיף qid ל‑`qids.js` לשתי השאילתות ולהעביר את `initialForum`
לעבוד עם `queId`. חשוב לשים לב שהשאילתה הראשונה פרמטרית ב‑`myId` והשנייה
ברשימת מזהי פורומים — צריך qid עם משתנים, לא אינטרפולציה של מחרוזת.

> זו גם דוגמה טובה לכך ששווה בדיקה אוטומטית שמריצה טעינת עמוד מול build
> פרודקשן ונופלת על כל 4xx/5xx בקונסול. הבאג הזה גלוי בשנייה הראשונה של
> כל עמוד, ובכל זאת חי בפרודקשן.

הפרופיל שנוצר ב‑`/me` בסוף התהליך: *React · NodeJs · ממשל נתונים · תיקון
מחשבים · ניהול · Jira api · הנחייה · API · סקירת קוד*, ובתפקידים *בניית
אפליקציות · משאבי אנוש · מרצה*. משתמש שכתב על עצמו שהוא מפתח JavaScript
מקבל פרופיל שאומר שהוא מתקן מחשבים ומרצה למשאבי אנוש.

**הסיבה:** `src/lib/embed/matcher.ts:17-20`

```ts
const THRESHOLDS = {
    MATCH: 0.88,
    SUGGESTION: 0.72,
};
```

סף של **0.72** על embeddings של Gemini הוא נמוך מדי בסדר גודל. כמעט כל שני
מונחים מאותו תחום סמנטי רחב ("תוכנה", "עבודה") חוצים אותו. בנוסף
`matchOne` מושך `queryNearest(namespace, vector, 1)` — **מועמד יחיד בלבד**,
כך שאין שום דרך להציע "התכוונת ל…?" או לזהות שהמועמד היחיד גרוע.

**עוד באותו payload:**
- **`existingId: "386"` נשלח שלוש פעמים** באותה בקשה (שלושה קלטים שונים
  התמפו לאותה מיומנות). אין דה‑דופליקציה לפי `existingId` ב‑`buildPayload()`.
- נשלחו 15 כישורים, השרת החזיר `counts.skills: 11`. ארבעה פריטים נעלמו
  בשקט, בלי הודעה למשתמש. אותו דבר בתפקידים: 7 נשלחו, 6 חזרו.

**הצעות תיקון:**
1. להעלות את `SUGGESTION` משמעותית (0.83–0.86) ולכייל מול קורפוס אמיתי.
2. למשוך `topK: 3-5` ולהציג למשתמש בחירה בין המועמדים במקום מועמד יחיד.
3. לעשות dedupe לפי `existingId` ב‑`buildPayload()`.
4. להחזיר למשתמש כשפריט לא נשמר, במקום להשמיט בשקט.

## 3. 🔴 חמור — סיום האונבורדינג לא מפעיל חישוב התאמות

אחרי שהשלמתי את כל התהליך והפרופיל מכיל 9 כישורים, 6 תפקידים, 5 ערכים
ו‑3 דרכי עבודה, מסך הלב `/lev` עדיין מציג:

> "לא נמצאו הצעות או פעולות עבורך, מומלץ לגשת לעמוד הפרופיל כדי להוסיף
> כישורים, משאבים או כדי ליצור ריקמה חדשה, בהצלחה"

כלומר המערכת שולחת את המשתמש לעשות בדיוק את מה שהוא זה עתה סיים לעשות.

**הסיבה:** לפי `docs/PLAN_MATCH_SUGGESTIONS.md` ההצעות מחושבות מראש בשרת,
ומתעדכנות מתוך הפעולות שמשנות פרופיל. `updateUserRelation.ts:2` אכן קורא
ל‑`matchUserToOpenEntities`:

```
src/lib/server/actions/configs/updateUserRelation.ts:2:
  import { matchUserToOpenEntities } from '$lib/server/matching/engine';
```

אבל האונבורדינג **לא עובר דרך הפעולה הזאת** — הוא כותב ישירות דרך
`src/routes/api/onboard/save/+server.ts`, ובקובץ הזה אין שום import
מ‑`$lib/server/matching/`. הנתיב שדרכו נכנס *כל משתמש חדש* הוא בדיוק
הנתיב היחיד שלא מפעיל את המנוע.

**התיקון:** לקרוא ל‑`matchUserToOpenEntities` (או להריץ את
`refreshMySuggestions`) בסוף `/api/onboard/save`, אחרי שהיחסים נשמרו.

זה מצטרף ל‑#2: גם אם ההתאמות היו רצות, הן היו רצות על כישורים שגויים.
שני הליקויים יחד מייצרים חוויה של "נרשמתי, מילאתי הכל, ואין כלום".

## 4. 🟠 קוקי `jwt` נשמר כמחרוזת `"undefined"`

`src/routes/signup/+page.server.js:110`:

```js
const { jwt, user } = await res.json();
…
cookies.set('jwt', jwt, { ...cookieOptions, httpOnly: true });
```

כשאישור מייל מופעל ב‑Strapi, `/api/auth/local/register` מחזיר `jwt: null`.
התוצאה היא קוקי אמיתי בשם `jwt` שערכו המחרוזת `undefined`. זה מייצר שגיאה
בקונסול כבר במסך `/signup/check-email` — לפני שהמשתמש בכלל אישר מייל:

```
[SocketClient] Authentication failed: Invalid or expired JWT
```

**התיקון:** `if (jwt) cookies.set('jwt', …)`, ובמקביל לוודא ש‑`SocketClient`
לא מנסה להתחבר בלי טוקן תקין.

## 5. 🟠 רענון במסך הסקירה מוחק את כל ניתוח ה‑AI

תוצאות הניתוח נשמרות רק ב‑`sessionStorage` תחת `onboard.cvResult`
(`review/+page.svelte:57`), וכשהמפתח חסר הדף מפנה בשקט חזרה:

```js
if (!data) {
    goto('/onboard/provider');
    return;
}
```

**מה שקורה בפועל:** רענון, "אחורה־קדימה", או פתיחת הקישור בטאב חדש במסך
שלב 5 — והמשתמש נזרק לשלב 4 בלי שום הודעה, וכל הניתוח (שלקח ~30 שניות
של קריאת AI, ועוד דקתיים של כתיבה) אבד. שחזרתי את זה: ניווט ישיר ל‑
`/onboard/provider/review` מחזיר תמיד ל‑`/onboard/provider`.

**התיקון:** לשמור את תוצאת הניתוח בצד שרת (או לפחות ב‑`localStorage`),
ולהציג הודעה במקום redirect שקט.

## 6. 🟠 22 מתוך 31 פריטים מסומנים כמבוטלים כברירת מחדל

`review/+page.svelte:81-83`:

```js
for (const r of m) chipState[`${cat}:${r.input}`] = 'on';   // matched
for (const r of n) chipState[`${cat}:${r.input}`] = 'on';   // new
for (const r of s) chipState[`${cat}:${r.input}`] = 'off';  // suggestions
```

בריצה שלי: `זוהו 31 פריטים · 0 אצלנו · 22 הצעות · 9 חדשים` — כלומר **22
מתוך 31 כבויים**. שתי בעיות:

**א. הוויזואל אומר "מחקתי", לא "לא נבחר".** מדדתי את הסגנון בפועל:

```
? שיתוף פעולה | text-decoration=line-through | opacity=0.45 | class="chip suggested off"
```

קו חוצה + שקיפות 0.45 נקראים כ"פריט שהוסר", לא כ"פריט שממתין לאישור".
משתמש שמסתכל על המסך רואה שרוב מה שה‑AI מצא כבר נמחק.

**ב. הטקסט בסעיף המשימות סותר את המצב.** הכותרת אומרת
"לחיצה על משימה להסרה" — אבל כל שמונה המשימות מוצגות כבר מחוקות. ההוראה
וההתנהגות הפוכות.

**ג. ההיגיון עצמו הפוך.** דווקא הפריטים שהותאמו לטקסונומיה הקיימת של
האתר — אלה שמחברים את המשתמש למנוע ההתאמות — הם שכבויים, בעוד פריטים
חדשים לגמרי דלוקים.

**התיקון:** הצעות דלוקות כברירת מחדל עם אינדיקציה ויזואלית של "לאישור"
(למשל מסגרת מקווקוות) במקום קו חוצה; ולתקן את טקסט ההסבר בסעיף המשימות.

<a id="7"></a>
## 7. 🟠 הצ׳יפ מציג מילה אחת ושומר מילה אחרת

זה מה שמסתיר את באג #2 מהמשתמש.

**התצוגה** (`review/+page.svelte:285-295`) — עבור הצעה מוצג הקלט של המשתמש:

```svelte
{#each sugg as r (r.input)}
  <button class="chip suggested" …>
    {on ? '✓' : '?'}
    {r.input}          ← המילה שהמשתמש כתב
  </button>
```

**השמירה** (`buildPayload()`, אותו קובץ) — עבור אותה הצעה נשלח הלייבל הקיים:

```js
const useExisting = r.status === 'matched' || r.status === 'suggestion';
out[cat].push(useExisting && r.existingId
    ? { name: r.existingLabel ?? r.input, existingId: String(r.existingId) }
    : { name: r.input });
```

כך שהצ׳יפ אומר "בסיסי נתונים", ומה שנשמר הוא "ממשל נתונים". למשתמש אין שום
דרך לראות את זה עד שהוא מגיע ל‑`/me` ומגלה פרופיל זר. אצל פריטי `matched`
המצב תקין — שם מוצג `r.existingLabel ?? r.input`.

**התיקון:** להציג בצ׳יפ של הצעה את הלייבל שייכתב, למשל
`בסיסי נתונים ← ממשל נתונים`, כך שהמיפוי גלוי לפני האישור.

## 8. 🟠 הצ׳קבוקס של ההסכמה הבסיסית לא נגיש

ב‑`/hascama`, ה‑`input[type=checkbox].checkbox-input` מוסתר ויזואלית ואינו
עטוף ב‑`<label>`. לחיצה על הטקסט "קראתי והסכמתי להסכמה הבסיסית" לא מסמנת
אותו — נאלצתי לקרוא ל‑`.click()` ישירות על האלמנט דרך JS.

**המשמעות:** משתמש שמנווט במקלדת או בקורא מסך לא יכול לאשר את התנאים,
והכפתור "להרשמה" לא ייפתח. זה חוסם לגמרי את ההרשמה עבורו — בשער הכניסה
היחיד למערכת.

**התיקון:** לעטוף את הקלט ואת הטקסט ב‑`<label>` משותף (או `id`+`for`),
ולהשאיר את הקלט מוסתר בטכניקת `sr-only` ולא ב‑`display:none`.

## נספח — איך שוחזרה הבדיקה

הבדיקה רצה מדפדפן Chromium אמיתי דרך Playwright, בפרופיל מתמיד כדי לשמור
קוקיז בין השלבים. כל שלב תועד בצילום מסך ובלוג של בקשות כושלות ושגיאות
קונסול.

השלבים שבוצעו, לפי הסדר:

1. `/hascama` — מילוי שם, מדינה (ישראל), מייל, סימון ההסכמה הבסיסית → `fp=823`
2. `/signup` — סיסמה → יצירת המשתמש (id 256) → `/signup/check-email`
3. `tovmeod.1lev1.com/api/auth/email-confirmation?confirmation=…` → `/login`
4. `/login` → `/onboard`
5. `/onboard` → מסלול "רוצה להציע כישורים" → `/onboard/provider`
6. `/onboard/provider` → "תיאור במילים שלך" → טקסט חופשי → ניתוח AI
7. `/onboard/provider/review` — סימון כל הפריטים → שמירה → `/onboard/provider/manual`
8. `/me` — אימות מה נשמר בפועל מול מה שהוצג
9. סריקה של `/lev`, `/me`, `/hub`, `/moach`, `/project`, `/gift`, `/demand`,
   `/consensus`, `/availableMission`, `/availiableResorce`, `/guid`, `/quorum`

**הערה על הסביבה:** פרוקסי היציאה של סביבת הבדיקה מנתק את לחיצת היד של
TLS מ‑Chromium (curl ו‑openssl עוברים; הדפדפן מקבל `ERR_CONNECTION_RESET`
מיד אחרי `200 Connection Established`). כדי לגלוש נדרש ריליי מקומי שמסיים
את ה‑TLS מול הדפדפן ופותח אותו מחדש מול היעד דרך ה‑TLS של Node. זה עניין
של סביבת ההרצה בלבד ואינו מעיד על שום דבר באתר.
